## 1. 지난 학기 수행 내용

### 1.1 요구사항 분석 및 시스템 개념 정의

지난 학기에는 학사관리 챗봇 시스템 개발을 위한 기초 설계를 수행하였다. 목표는 완성된 시스템 구현이 아니라, 이후 개발 단계에서 혼선 없이 작업을 진행할 수 있도록 프로젝트의 범위, 기능, 데이터 구조를 명확히 정리하는 데 있었다. 요구사항 분석, 유스케이스 도출, 데이터베이스 스키마 설계, 기술 조사, 역할 분담을 중심으로 설계를 진행하였다.

기존 학사정보 시스템은 메뉴 탐색 방식이 중심이어서 사용자가 원하는 정보를 찾기까지 여러 단계를 거쳐야 했다. 자주 사용하지 않는 메뉴는 찾기 어렵다는 문제도 존재했다. 이러한 한계를 바탕으로 자연어 질문으로 정보를 조회하는 챗봇 시스템의 필요성을 도출하였다. 주요 시나리오는 다음과 같이 정리하였다.

- 등록금 확인
- 수강 과목 조회
- 성적 확인
- 시간표 조회
- 교수 정보 조회
- 졸업요건 확인

### 1.2 시스템 설계 (유스케이스, 아키텍처, DB)

유스케이스 다이어그램과 서술서를 작성하였다. 사용자는 학생으로 한정하고, 로그인 이후 자신의 학사 정보를 조회하는 흐름을 기본으로 설정하였다. 기능 요구사항과 비기능 요구사항도 구분하였다.

- **기능 요구사항**: 로그인, 수강 과목, 성적, 시간표, 교수 정보 조회
- **비기능 요구사항**: 응답 시간, 접근 제어, 질의 정확도, 오류 처리

아키텍처는 프론트엔드, 백엔드, 데이터 계층으로 분리하였다. 사용자가 React 기반 UI에서 질의를 입력하면 백엔드의 `QueryRouter`와 `ChatService`를 통해 적절한 처리 모듈로 전달되는 구조로 설계하였다.

- **구조화된 데이터**: `TextToSQLService`가 SQL을 생성하고 `DBExecutor`가 MySQL에 질의를 수행
- **비정형 데이터**: `EmbeddingService`와 Vector Search(FAISS 기반)를 활용한 처리 구조 고려
- **MCP 연계**: LLM과 데이터 계층을 연결하고, 결과를 자연어 응답으로 반환

데이터베이스는 `Student`, `Professor`, `Course`, `Enrollment`, `Schedule` 중심으로 설계하였다. ERD를 작성하고 DDL 기반 초기 구조를 정의하였으며, 샘플 데이터 구성 기준도 설정하였다. `Tuition`과 `Prerequisite`를 포함한 확장 구조도 함께 고려하였다.

### 1.3 기술 조사 및 구현 기반 준비

자연어 질의 처리와 데이터베이스 질의 변환 기술을 중심으로 조사하였다.

- MCP 구조를 분석하여 LLM 연계 방식 검토
- Spider Dataset, Seq2SQL 등을 통해 Text-to-SQL 방법론과 평가 방식 학습
- 벡터 데이터베이스 기반 문서 검색 방식 조사

지난 학기 결과는 요구사항 명세, 설계 문서, 데이터 구조, 기술 검토로 정리되며, 이는 이번 학기 구현의 기준이 된다.

## 2. 이번 학기 개발 목표

이번 학기의 목표는 지난 학기에 정리한 설계 결과를 바탕으로 실제로 동작하는 학사관리 챗봇 시스템을 구현하고, 이를 검증 및 개선하는 데 있다. 단순한 기능 시연이 아니라 핵심 기능이 안정적으로 동작하는 통합 시스템을 완성하는 것이 목표이다.

### 2.1 자연어 질의 처리 기능 구현

사용자가 자연어 문장으로 질문하면 이를 분석하여 적절한 SQL을 생성하고, 실행 결과를 자연어 또는 표 형태로 제공한다. 단일 엔드포인트 `POST /chat` 안에서 `QueryRouter`가 메시지를 분류하고, DB 분기에서는 LLM 후보 SQL과 키워드 룰 후보 SQL을 순서대로 시도해 답변한다. 휴학·복학·장학·졸업요건 같은 일반 학사정보 질문은 참고문서 RAG 경로로 흐른다.

### 2.2 인증 및 접근 제어 구현

학생은 학번과 비밀번호로 로그인하며, 이후의 모든 질의는 본인 학사정보 범위로 제한한다. SQL 가드(`sql_guard`)가 `student/enrollment/tuition` 테이블 사용 시 `WHERE student_id = :student_id` 바인딩 등장을 강제하고, `SqlExecutor`는 호출자가 다른 학번을 주입하더라도 인증된 학생 ID로 덮어쓴다. 학번 리터럴(`= 202214001`)은 정규식으로 거부한다.

### 2.3 핵심 기능 및 UI 통합

학생 기본 정보 조회, 수강 과목, 성적, 시간표, 교수 정보, 등록금, 선수과목 조회 기능을 통합적으로 구현한다. 결과 표시 형식은 행 수에 따라 자동 분기한다(`display_format`). 2건 이상은 한국어 헤드라인 + 표 컴포넌트, 단건은 LLM 산문, 0건은 안내 메시지.

### 2.4 테스트 및 완성도 향상

`pytest` 기반 단위·통합 테스트를 도입해 보안 가드(`sql_guard`)·라우팅(`QueryRouter`)·`ChatService` 분기를 자동 회귀 검증한다. 외부 의존(OpenAI/Upstage/임베딩 모델)은 키 미설정 시 자연스럽게 폴백하도록 설계되어 있어, 테스트는 결정론적으로 5초 내 실행된다.

## 3. 시스템 개발 범위

본 프로젝트의 개발 범위는 학생이 자신의 학사정보를 자연어로 조회할 수 있도록 지원하는 **학생 전용 서비스**에 한정된다. 학사관리 전체 시스템을 재구축하는 것이 아니라, 학생이 자주 필요로 하는 정보를 대화형으로 제공하는 지능형 조회 서비스 구현에 초점을 둔다.

### 3.1 기능적 범위

- **사용자 인증**: 로그인, 로그아웃 (로그인 이후에만 질의 기능 사용 가능)
- **DB 기반 학사정보 조회**: 본인 정보, 수강 과목, 성적, 시간표, 교수 정보, 등록금, 선수과목
- **참고문서 기반 학사정보 조회**: 휴학·복학·장학·졸업요건·신입생 가이드북·국제교류 등 PDF에서 검색
- **챗봇 대화 기능**: 위 두 경로를 자연어 단일 입력으로 통합

### 3.2 데이터 범위

- **DB**: 모의 학사 데이터베이스. 기본 테이블(`Student`/`Professor`/`Course`/`Enrollment`/`Schedule`) + 확장 테이블(`Tuition`/`Prerequisite`) + 운영 테이블(`QueryLog`/`ReferenceDocument`/`ReferenceChunk`).
- **참고문서**: 건국대 공식 PDF 5종 (신입생 가이드북, 장학금 3건, 국제교류 1건). Upstage Document Parser로 파싱·청킹하여 FAISS 인덱스에 저장.

### 3.3 개인정보 범위

주소, 주민등록번호, 연락처, 보호자 정보 등 민감한 정보는 다루지 않는다. 학번, 이름, 전공, 과목, 성적, 시간표, 교수 이메일, 등록금 납부 상태 등 학사정보 조회 목적에 필요한 데이터만 사용한다. 모든 시드 데이터는 가짜이며, LLM에 row를 그대로 송신하는 것도 정책상 허용된다.

### 3.4 비기능적 범위

- **응답 시간**: DB 다건 응답은 LLM 호출 없이 표로 즉답. 단건/RAG 응답만 LLM 호출 1회.
- **보안**: SELECT 전용 가드, 학번 리터럴 차단, `:student_id` 바인딩 강제.
- **회귀 방어**: pytest 69개로 핵심 분기 검증.

## 4. 적용 대상 DB 스키마

본 프로젝트의 데이터베이스는 학생 전용 학사정보 챗봇이 처리해야 할 핵심 정보를 저장하고 조회할 수 있도록 설계된 모의 학사정보 데이터베이스이다.

### 4.1 기본 테이블

| 테이블 | 설명 |
|--------|------|
| `student` | 학번, 이름, 전공, 입학년도, 상태, 비밀번호 해시. 인증과 권한 제어의 기준 |
| `professor` | 교수 ID, 이름, 이메일, 연구실. 시드는 `prof001@konkuk.ac.kr` / `공A301호` 패턴 |
| `course` | 과목 ID, 담당 교수 ID, 과목명, 학점, 강의실, 설명 |
| `enrollment` | 학생-과목 간 수강 관계, 학기, 성적 |
| `schedule` | 과목별 수업 요일, 시작/종료 교시, 강의실 |

### 4.2 확장 테이블

| 테이블 | 설명 |
|--------|------|
| `tuition` | 학기별 등록금과 납부 상태 |
| `prerequisite` | 자기참조형 보조 테이블, 선수과목 관계 |

### 4.3 운영 테이블

| 테이블 | 설명 |
|--------|------|
| `query_log` | 모든 질의 기록. `route`/`success`/`error`/`generated_sql`로 시연 통계 가능 |
| `reference_document` | 인제스트된 PDF 메타 + 파싱 결과 경로 + status |
| `reference_chunk` | 청크 본문 + heading + 페이지 + FAISS `vector_id` |

### 4.4 테이블 간 관계 활용

- **성적 조회**: `student` × `enrollment` × `course`
- **교수 이메일 조회**: `course` × `professor`
- **시간표 조회**: `enrollment` × `course` × `schedule`
- **등록금 확인**: `tuition`
- **선수과목 조회**: `prerequisite`

## 5. 요구사항 반영 방향

본 프로젝트는 요구사항 정의서를 실제 구현 가능한 시스템으로 구체화하는 것을 목표로 한다. 요구사항 반영은 단순히 기능을 추가하는 수준이 아니라, 정의된 요구사항이 시스템 내부에서 어떻게 구현되고 검증될 것인지까지 포함한다.

### 5.1 기능 요구사항

기능 요구사항은 인증, 라우팅, 조회의 세 축으로 반영한다.

- **인증**: PBKDF2 비밀번호 해싱 + 자체 JWT(HS256). `Authorization: Bearer` 헤더로 모든 API 호출 인가.
- **라우팅**: `QueryRouter`가 메시지를 분류 — 과목명 + DB 키워드 → `db`, 참고문서 키워드 → `reference_rag`, DB 키워드 → `db`, 그 외 → 기본 `reference_rag`.
- **조회**:
  - DB 분기: `TextToSQLService`가 LLM/룰 두 후보 SQL을 생성, `SqlExecutor`가 가드 검증 + `:student_id` 강제 바인딩 후 실행, `ResultSummarizer`가 표/산문 분기.
  - RAG 분기: KURE-v1 임베딩 → FAISS 검색(top_k=5) → OpenAI Responses로 청크 기반 답변 합성, 출처 표기 강제.

### 5.2 검색 범위 제한

- DB: 화이트리스트 테이블만 허용. 외부 테이블 참조 시 가드가 거부.
- RAG: `ReferenceDocument.status == "ready"`인 청크만 검색 대상.
- LLM 프롬프트에 스키마 정보를 명시적으로 삽입.

### 5.3 성능 요구사항

- **응답 시간**: DB 다건 응답은 LLM 호출 없음(C 변경). 단건/RAG 응답만 LLM 1회.
- **정확도**: LLM SQL이 가드 거부되거나 빈 결과면 룰 fallback이 자동 시도(B 변경). 두 후보가 모두 실패하면 RAG로 폴백.
- **임베딩 가정**: `extract_chunks(max_chars=1800) < _embedding_text(max_chars=2500)`을 유지해야 검색 임베딩과 LLM 컨텍스트가 일치한다(E, 주석으로 명시).

### 5.4 보안 요구사항

- DB 계정: SQLite 파일에 직접 접근. 가드가 SELECT 외 명령을 차단.
- 학번 스코프: `:student_id`를 `SqlExecutor`가 강제 주입, 호출자 임의 입력 무시.
- 학번 리터럴 차단: 정규식으로 `student_id = <숫자>` / `IN (..)` 등 거부.
- LLM 프롬프트도 동일 규칙 명시(다중 방어).

### 5.5 운영 가시성 (H 추가)

- `query_log.route`: `general` / `db` / `db_no_result` / `reference_rag` / `reference_rag_after_db_failed`.
- `query_log.success`: 사용자에게 의미 있는 답변 여부.
- `query_log.error`: 실패 사유 누적 (`llm_sql_rejected_by_guard`, `rule_sql_no_rows` 등).
- 발표 자료에서 라우팅 분포·실패 패턴을 통계로 활용 가능.

### 5.6 확장성과 유지보수

- 서비스 6개로 분해되어 각 책임이 분리됨. 라우터를 LLM 분류기로 교체하거나 RAG 검색을 MMR로 바꾸는 등 부분 교체가 용이.
- 새 문서 종류는 `ReferenceDocument.category`로 분류만 추가하면 됨.

## 6. 세부 추진 내용

이번 학기 프로젝트는 실제 동작 가능한 학사관리 챗봇 시스템 구현을 위해 여러 개발 영역을 유기적으로 연결하여 추진한다. 주요 추진 영역은 다음과 같다.

### 6.1 백엔드 구축 (완료)

`ChatService`(조율) / `QueryRouter`(분류) / `TextToSQLService`(SQL 생성) / `SqlExecutor`(가드+실행) / `ResultSummarizer`(요약·표 분기) / `ReferenceRAGService`(RAG)의 6개 서비스로 분해하였다. 단일 엔드포인트 `POST /chat`이 모든 채팅 요청을 받아 `ChatService.answer`로 위임한다. 인증은 `auth.py` 라우터와 `deps.get_current_student` 의존성으로 처리한다.

### 6.2 Text-to-SQL 구현 (완료)

`TextToSQLService`가 두 메서드를 제공한다.

- `generate_with_llm`: OpenAI Responses(JSON)로 자연어 → SQL.
- `generate_with_rules`: 키워드별 7개 fallback 룰(등록금/성적/시간표/교수/선수/내정보/수강).

`ChatService._answer_from_db`가 두 후보를 순서대로 시도하고, 가드 거부·실행 예외·빈 결과 등 모든 실패 사유를 `DbAttempt.errors`에 누적하여 `query_log`에 남긴다.

### 6.3 데이터베이스 구축 (완료)

`init_db.py`가 부팅 시 한 번 시드를 적재한다. 2026-1학기 실제 과목 13개, 학생 100명(학번 `202214001`–`202214100`), 학생당 5과목 수강·등록금 1행, 선수과목 7쌍. 교수 시드는 가짜 패턴(`prof{NNN}@konkuk.ac.kr` / `공A{300+i}호`)으로 정상화하였다(I 변경).

### 6.4 RAG 파이프라인 구축 (완료)

오프라인 인제스트 스크립트 `python -m app.scripts.ingest_documents`가 `data/raw_documents/`의 PDF를 Upstage Document Parser로 파싱, 청크화(`max_chars=1800`), KURE-v1 로컬 임베딩, FAISS 인덱스 빌드까지 일괄 처리한다. 런타임 RAG는 인덱스만 읽어 사용하므로 Upstage API 키 없이 동작한다.

### 6.5 프론트엔드 개발 (완료)

React 19 + Vite 6 SPA. `LoginPage` / `ChatPage` / `MessageBubble` / `RowTable` 컴포넌트와 `api/client.js` fetch 래퍼. `displayFormat === 'table'`일 때 `RowTable`이 컬럼 라벨(영→한 매핑)과 셀 포맷(금액 쉼표, 납부 "완납/미납")을 처리한다. 라우팅 라이브러리 없이 토큰 유무로 화면 토글.

### 6.6 시스템 통합 (완료)

응답 스키마 `ChatResponse`가 두 경로에서 동일(`route`/`answer`/`display_format`/`sql?`/`rows`/`sources`). 프론트가 단일 형식만 처리하면 됨. `ChatService` 내부 메타 라우트(`db_no_result`, `_after_db_failed`)는 로그에만 기록, 사용자 응답은 `general`/`db`/`reference_rag` 셋만 노출.

### 6.7 예외 처리 및 오류 대응 (완료)

- 모호한 SQL이 가드에 걸리면 errors에 사유 누적 후 다음 후보 시도.
- 두 후보 모두 빈 결과면 "조회 결과가 없습니다…" 안내.
- 두 후보 모두 실행 못하면 RAG로 폴백.
- 인증 실패(토큰 만료/없음)는 401.

## 8. 테스트 계획

본 프로젝트는 자연어 기반 학사정보 조회 시스템이므로 기능 구현만으로는 품질을 보장할 수 없다. 자동화 테스트와 수동 시연 검증을 병행한다.

### 8.1 자동화 테스트 (pytest)

| 영역 | 테스트 수 | 핵심 검증 |
|------|----------|-----------|
| `sql_guard` | 21 | 학번 리터럴 차단, 미바인딩 거부, DROP/INSERT 차단 |
| `TextToSQLService` | 14 | fallback 룰 7분기 SQL 생성, course_filter |
| `GeneralAnswerService` | 5 | KST 시간 정확성 (freezegun) |
| `ResultSummarizer` | 4 | 행 수 → display_format 분기 |
| `QueryRouter` | 11 | A 변경 회귀 ("내 휴학" → RAG, "교수" 단독 → RAG) |
| `SqlExecutor` | 6 | `:student_id` 강제 주입, 학생 간 데이터 격리 |
| `ChatService` | 14 | LLM→룰 폴백, 표/산문 분기, query_log 의미 |
| **합계** | **69** | 5초 내 결정론적 실행 |

OpenAI 키는 `conftest.py`가 `OPENAI_API_KEY=""`로 강제. LLM 호출은 자연스럽게 None 폴백되며, 의미 있는 값이 필요한 3개 테스트만 `monkeypatch`로 1줄씩 패치.

### 8.2 수동 시연 시나리오

`ChatPage.jsx`의 8개 예시 버튼:
- DB 분기: "내 수강 과목", "내 성적", "오늘 시간표", "데이터베이스 교수님 이메일", "이번 학기 등록금", "운영체제 선수과목".
- RAG 분기: "휴학 신청은 어떻게 해?", "졸업 요건 알려줘".

각 시나리오에 대해 응답 정확성, 표/산문 형식 적합성, 출처 표기, 응답 시간을 점검한다.

### 8.3 보안 테스트

`sql_guard` 자동 테스트가 다음을 모두 거부함을 검증:
- `SELECT * FROM enrollment WHERE student_id = 202214002` (학번 리터럴)
- `SELECT * FROM enrollment` (바인딩 누락)
- `SELECT student_id FROM enrollment` (SELECT절만 등장)
- `DROP TABLE student` / `INSERT INTO ...` (비-SELECT)
- `SELECT * FROM secret_table` (테이블 화이트리스트)

`SqlExecutor` 통합 테스트가 호출자가 `params={"student_id": 202214002}`를 주입해도 인증된 학생 ID로 덮어씀을 검증.

## 9. 기대 효과

본 프로젝트의 기대 효과는 네 측면에서 정리할 수 있다.

1. **사용자 편의성 향상**: 학생은 메뉴를 여러 단계 탐색하지 않고도 자연어 질문만으로 필요한 학사정보를 빠르게 확인할 수 있다.
2. **기술적 가능성 검증**: Text-to-SQL과 RAG를 한 챗봇에 결합한 실제 응용 사례로서, 두 패러다임의 분기·통합 운영 노하우를 보여준다.
3. **실무형 개발 역량 강화**: 요구사항 분석, DB 설계, 백엔드/프론트엔드 구현, 시스템 통합, 보안 강화, 테스트 자동화, 문서화까지 포함하는 전 과정을 경험한다.
4. **향후 확장 가능성 확보**: 새 문서 종류는 `ReferenceDocument.category`로, 새 라우팅 정책은 `QueryRouter`로, 새 답변 형식은 `display_format` 추가로 확장 가능. 서비스 분해 덕에 부분 교체 비용이 낮다.

## 10. 결론

본 프로젝트는 학생이 자연어를 이용하여 자신의 학사정보를 손쉽게 조회할 수 있도록 지원하는 학사관리 챗봇 시스템 개발을 목표로 한다. 기존 학사정보 시스템의 메뉴 기반 구조에서 발생하는 불편을 줄이고, 자연어 인터페이스를 통해 보다 직관적이고 사용자 친화적인 정보 조회 방식을 제공하고자 한다.

이번 학기에는 지난 학기 설계를 바탕으로 단일 엔드포인트 챗봇을 구현하고, 6개 서비스로 분해하여 각 책임을 분리하였다. SQL 가드 강화·LLM/룰 폴백·표 분기·로그 의미화 등 9개 개선 항목을 순차 적용하였으며, 69개 자동화 테스트로 회귀를 방어한다. 다음 단계는 다이어그램 3종과 요구사항 분석서 갱신본을 작성하여 코드와 문서의 1:1 대응을 완성하는 것이다.

본 프로젝트는 학사정보 접근의 편의성을 높이는 동시에, 인공지능 기반 질의 처리 기술이 실제 정보 시스템에서 어떻게 활용될 수 있는지를 검증하는 사례가 될 수 있다. 향후 졸업요건 분석, 등록금 조회, 공지사항 검색, FAQ 응답 등으로 확장할 수 있는 기반을 제공한다는 점에서도 충분한 발전 가능성을 가진다.
